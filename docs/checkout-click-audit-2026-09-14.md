## 로그가 없다고 미클릭으로 판정할 수 없는 이유

0.6.0의 `traceLock()`은 유효한 실제 출결 테스트 토큰이 있을 때만 버튼 클릭 문구를 기록합니다. 일반 예약으로 실행된 자동 출결은 테스트 토큰이 없어 클릭해도 이 문구가 잠금 테스트 로그에 들어가지 않습니다. 내보내기도 잠금 테스트 현재 1개와 과거 최대 10개만 포함합니다. 일반 출결의 `chrome_pending`, `last_failure`, 날짜별 앱 동작 로그는 업로드하지 않았습니다. 앱의 로그 수집에서 누락된 부분입니다.

[0.6.0 클릭 경로와 테스트 한정 기록](https://github.com/dnjsml0206-blip/classroom-attendance-android/blob/v0.6.0/app/src/main/java/net/tacademy/attendance/ChromeAttendanceService.java#L160) · [내보내기 범위](https://github.com/dnjsml0206-blip/classroom-attendance-android/blob/v0.6.0/app/src/main/java/net/tacademy/attendance/LockLogExport.java#L59)

배포된 0.6.0과 0.6.1의 `ChromeAttendanceService.java`는 동일했습니다. 앞선 작업에서 추가한 일반 `BUTTON_REQUEST`·`BUTTON_FAILED`·`CONFIRM_REQUEST` 진단은 조사 당시 미배포 코드였습니다. 이후 v0.7.0을 설치해도 오늘 과거 클릭을 소급 기록할 수 없습니다.

## ‘클릭 결과 확인’ 카드의 의미

사용자 확인: **카드 있음 / 오늘 보류 해제 안 함 / 언제 생겼는지 모름**.

배포 코드의 순서는 다음과 같습니다.

1. 클릭 가능한 출결 버튼을 찾고 시간·Wi-Fi 조건을 재확인합니다.
2. `chrome_pending`에 `날짜:ENTRY` 또는 `날짜:CHECKOUT`을 동기 저장합니다.
3. 시간을 다시 확인한 뒤 Android `ACTION_CLICK`을 요청합니다.
4. 요청이 `false`로 반환되면 표식을 지웁니다. `true`이고 출결 결과가 확인되지 않으면 표식이 남습니다.
5. 출결 완료 관찰 또는 사용자의 보류 해제는 표식을 지울 수 있습니다.

따라서 정상 실행 흐름에서는 ‘클릭 요청은 받아들여졌지만 결과를 확인하지 못한 상태’와 맞는 흔적입니다. 다만 저장 직후·클릭 전 앱이 종료되거나 저장/실행이 중단되어도 표식이 남을 수 있습니다. 표식만으로 클릭 실행을 확정하지 않습니다. 이전 날짜의 입실 표식도 같은 카드를 만들 수 있습니다.

## 버튼 클릭·확인·서버 처리는 서로 다른 단계

기존에 저장한 사이트 HTML의 `goOutClass()`는 **퇴실 버튼 → ‘정말로 퇴실 하시겠습니까?’ 확인창 → 확인 선택 → `PresentOut_ok.asp` 요청** 순서입니다. 실제 HTTP 응답이나 현재 서버 동작을 이번 조사에서 측정한 것은 아닙니다.

- 최초 퇴실 버튼 클릭만으로 서버 요청까지 갔다고 단정할 수 없습니다.
- 확인창의 확인을 눌러 서버 요청을 보내도 서버 오류로 기록 저장이 실패할 수 있습니다.
- 출석 시각 미반영으로 앞의 클릭 유무를 역추론하지 않습니다.
- 서버에 요청 흔적이 있어도 같은 Chrome에서 사람이 눌렀는지 앱이 눌렀는지는 별도 시각·기기 증거가 필요합니다.

## 다음 확인에 필요한 원본

우선 휴대폰 내부의 `chrome_pending`이 `2026-09-14:CHECKOUT`인지 읽어 날짜와 출결 단계를 확인해야 합니다. 날짜별 앱 로그와 마지막 실패 표식이 남아 있다면 함께 대조할 수 있습니다. 이들 또한 직접적인 클릭/확인창 실행 이력은 아니므로 남아 있는 내용에 따라 확정 범위가 달라집니다.

현재 이 PC에서 ADB로 읽을 수 있는 실기기는 0대였습니다. USB 디버깅이 허용된 해당 휴대폰이 연결되면 출석 앱의 해당 항목만 읽어 추가 확인할 수 있습니다. 확인 전 ‘확인 후 보류 해제’를 누르면 남은 단서를 지우므로 보류 표식은 유지합니다.
