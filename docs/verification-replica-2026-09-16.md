## 수정 전 관찰과 오늘 로그의 관계

기존 APK에서는 정상 입실이 성공했고, Chrome을 다른 앱 화면으로 가린 시나리오에서는 클릭 0건 상태로 35초 만에 TIMEOUT_CHROME_NOT_VISIBLE 및 자동 보류가 재현됐다. 정상 입실 10개 확인, 중단 재현 11개 확인을 통과했다. 이는 오늘 로그에 나타난 '클릭 전 화면 판독 실패가 이후 자동 시도까지 막음'이라는 코드상의 문제를 입증한다. 오늘 실제 휴대폰에서 어떤 화면이 포커스를 가져갔는지까지 확정한 것은 아니다.

초기 정상 페이지 시험 중에는 버튼이 보이는데 BUTTON_UNAVAILABLE로 끝난 사례도 있었다. UI Automator는 동일 input을 text=입실, clickable=true, enabled=true로 읽었다. 이후 기존 APK 재시험은 성공했으므로 캐시가 유일한 원인이라고 단정하지 않는다. 수정본은 동적 버튼·창 상태를 새로 읽도록 보강했고 정상·지연·화면 복귀 시험에서 클릭과 시간 확인이 모두 성공했다.

시험 도구 준비 단계의 디버깅 포트·새 탭 연결 실패는 앱 회귀 성공 건수에 포함하지 않았다. 새 탭 초기화 대기를 풀면서 Fetch interception을 준비하는 방식으로 수정한 뒤 비교했다.

## 반영 사항

1. 클릭 전 Chrome 화면/주소 판독이 끊기면 초기 35초 뒤 한 번만 복구 관찰을 연장한다. 페이지 대기는 시작부터 최대 70초, 클릭 후 결과까지 한 시도 전체 최대 105초다. 화면이 돌아오면 기존 페이지에서 이어서 확인하며 복귀 때문에 앱이 새 페이지를 열지 않는다.
2. 클릭 전의 화면·주소 판독 시간 초과, 화면 꺼짐, Wi-Fi 이탈을 클릭 후 결과 미확인과 분리했다. 전자는 한 시간대의 자동 처리를 영구 보류하지 않는다. 이후 접속에는 기존 자동 단계별 3회, 2분/5분 재접속 간격, 하루 20회 한도, 공통 3초 간격을 그대로 적용한다.
3. 버튼을 실제로 요청한 경우, 반환 거절 또는 서버 시간 미반영은 기존 보류 및 저장된 클릭 표식을 유지한다. 임의의 자동 재클릭을 추가하지 않았다.
4. 출결 화면을 읽을 때 Android 13 이상에서는 접근성 캐시를 비우고 현재 창을 다시 읽는다. 구버전은 루트 refresh를 사용한다. 텍스트·스크롤·창 변경 이벤트도 작업 중에 수신한다. 이는 로컬 화면 정보 갱신이며 웹 페이지 새로고침이 아니다.
5. CHROME_NOT_VISIBLE에 ROOT_UNAVAILABLE / SYSTEM_UI / OTHER_APP 분류를 추가했다. 개인 앱 이름·페이지 본문·쿠키는 내보내지 않는다. PAGE_RECOVERY_WAIT와 PRECLICK_DEFERRED도 진단과 분석기에 표시한다.
