## 지연 원인과 판단 범위

`AttendanceEngine.request()`가 **Wi-Fi가 없다고 확인하기 전에도 다음 실행을 60초 뒤로 미뤘습니다.** 이후 Wi-Fi 변경 콜백이 와도 이 제한에 걸려 무시되고, 30초 보조 감시 주기에서 다시 실행될 수 있었습니다. 이 문제는 v0.9.6에도 남아 있었습니다.

마지막 미연결 기록부터 Chrome 요청까지 60.129초입니다. 다만 구버전에는 실제 Wi-Fi 연결 완료·기본 인터넷 전환 시각이 없어 이 60.129초를 ‘Wi-Fi 연결 완료 후 지연’으로 단정할 수 없습니다. 앱 코드의 불필요한 대기는 확인했지만, Android의 Wi-Fi 검증에 걸린 시간과 앱의 대기 시간을 이번 로그만으로 정확히 분리할 수는 없습니다.

Wi-Fi는 인터넷 사용 가능 상태가 된 뒤에도 기본 인터넷 경로 선택이 늦을 수 있습니다. 기존 감시는 Wi-Fi 네트워크 변경만 구독하므로 기본 인터넷 전환 시점도 추가로 감지해야 합니다. [Android 네트워크 상태 공식 문서](https://developer.android.com/develop/connectivity/network-ops/reading-network-state)를 참고했습니다.

## 보완

- Wi-Fi가 준비되지 않은 확인은 60초 대기 시간을 소비하지 않습니다. 입실 시간대 첫 대상 Wi-Fi 연결이 준비되면 바로 자동 처리로 전달합니다.
- Wi-Fi 변화와 기본 인터넷 경로 변화를 모두 구독합니다. 콜백에서는 조회 작업을 예약하고, 연결 상태 갱신의 시차를 고려해 필요한 경우 1초 간격으로 최대 3회 추가 로컬 확인합니다. 이 확인은 사이트에 요청하지 않습니다.
- 이미 연결된 채 입실 시간이 시작된 경우에도 즉시 확인합니다. 새 날짜·입실/퇴실 구간은 앞 구간의 로컬 대기를 이어받지 않습니다.
- Wi-Fi 설정 도우미가 화면을 사용 중이면 대기를 소비하지 않고, 도우미 종료 직후 다시 확인합니다.
- 완료·예약 OFF·시간대 밖·휴강일 조건과 기존 사이트 접속 한도는 유지합니다. 연결 이벤트가 반복돼도 자동 재접속 간격(2분, 5분), 구간당 최대 3회, 결과 미확인 중단 조건을 초기화하지 않습니다.

## 다음 로그에서 보는 값

`NETWORK_STATE_CHANGED`는 로컬 확인에서 Wi-Fi 준비 상태 코드가 바뀐 시점입니다. `network_trigger`는 변경 콜백/로컬 확인 구분, `network_event_at_ms`는 해당 콜백을 앱이 받은 시각, `elapsed_ms`는 그 이후 준비 상태 관찰까지의 경과 시간입니다. 여러 콜백이 합쳐지면 마지막 콜백 기준입니다. SSID·비밀번호·페이지 원문은 이 이벤트에 저장하지 않습니다.

`AUTOMATIC_TRIGGER / WIFI_READY`는 준비된 연결을 자동 출결 흐름으로 넘긴 시점입니다. Chrome을 실제 열었다는 뜻은 아니며 `CHROME_OPEN_DISPATCHED`와 구분합니다. 두 이벤트 이후 버튼 클릭·사이트 시각 확인을 함께 보면 연결 대기, 잠금 처리, Chrome 로딩 중 어디서 지연됐는지 구분할 수 있습니다. `NETWORK_WATCH_FAILED`는 변경 감시 등록 실패이며, 이 경우 30초 보조 확인이 남습니다.

‘바로 시작’은 등록 Wi-Fi의 인터넷·기본 경로 조건이 확인된 직후 출결 흐름을 시작한다는 뜻입니다. Wi-Fi 이름이 표시되는 시각이나 서버 입실 기록이 완료되는 시각과 같지는 않습니다. 휴대폰의 네트워크 준비, 화면/신뢰 상태 확인, Chrome 로딩 시간은 별도로 필요합니다.
