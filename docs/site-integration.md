# 출석 사이트 연동 확인 절차

대상: https://skplanet.atosoft.net/Worknet/Present/Present.asp

## 현재 확인 수준

사용자에게서 다음 사실을 전달받았다.

- 모바일 Chrome에서 입실·퇴실 버튼을 눌러 처리한다.
- 지정 Wi-Fi에서만 처리가 허용된다.
- 일상 사용 중 재로그인을 요구받지 않았다.

외부 확인 도구에서 페이지를 열지 못했다. 이 결과만으로 서버의 접속 제한 방식이나 원인을 판단할 수는 없다.
HTML, 버튼 선택자, 처리 요청 URL, API 존재 여부, CSRF 토큰, 세션 만료 정책은 미확인이다.

## 1. 화면 및 인증 확인

- 개인정보를 가린 입실 전, 입실 후, 퇴실 후 화면
- 입실 불가 시간의 버튼 상태 및 안내 문구
- 최초 로그인 / 본인 인증 / 기기 등록 절차
- 로그아웃, 세션 만료, 연결 제한 화면
- 과정 또는 반을 선택하는 추가 단계의 유무

화면 캡처는 표시 상태 확인용이다. 캡처만으로 요청 방식이나 성공 판정을 확정하지 않는다.

## 2. 허용된 네트워크에서 요청 확인

실제 휴대폰 또는 적절한 진단 환경을 허용 Wi-Fi에 연결한 상태에서 확인한다.

- 정상 페이지 조회의 리디렉션과 인증 상태
- 정상 입실·퇴실 시 사용되는 HTTP 메서드, 경로, 폼 필드 및 토큰
- 서버가 요구하는 과정 ID, 날짜 및 기기 정보
- 추가 JavaScript 계산이나 본인 인증의 유무
- 성공·이미 처리됨·시간 제한·네트워크 제한·인증 만료 응답
- 처리 결과를 다시 조회할 수 있는 경로

읽기 전용 진단으로 가능한 항목부터 확인한다. 실제 출석 요청을 테스트할 때에는 현재 수업일과 사용자의 실제 출석 상황에 맞게 수행한다.

## 3. 성공 판정

- HTTP 200, 버튼 클릭 성공, 토스트 표시만으로 완료를 판정하지 않는다.
- 해당 날짜·과정의 입실 또는 퇴실 기록과 서버 결과를 확인한다.
- 요청 후 응답을 잃었으면 먼저 기록을 재조회한다.
- 화면이 예상과 다르면 자동 처리를 중지하고 점검 상태로 표시한다.

## 4. 구현 선택 기준

| 확인 결과 | 구현 방향 |
| --- | --- |
| 앱 자체 인증 및 정상 HTTP 요청 재현 가능 | 네이티브 요청 기반 처리 검증 |
| 페이지 JavaScript 실행 필요 | 앱 내부 웹 화면 기반 처리 검증 |
| Chrome 화면 상태에 강하게 의존 | 화면 조작 방식과 잠금 해제 필요성 검토 |
| 인증 또는 처리 구조를 확인할 수 없음 | 조회·알림 모드 유지, 실제 자동 처리 비활성 |

## 진단 자료 취급

- 쿠키, Authorization 헤더, 비밀번호, 전화번호, 학번 등의 개인정보를 커밋하지 않는다.
- 원본 HAR 및 HTML은 민감정보가 포함될 수 있어 기본적으로 저장소에서 제외한다.
- 진단 결과는 필드명, 상태 종류, 민감정보를 제거한 예시로 정리한다.
- 미확인 요청 URL이나 버튼 선택자를 추정해 실제 출석 연동 코드로 확정하지 않는다.
