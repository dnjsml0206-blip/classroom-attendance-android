퇴실 버튼 요청과 확인 버튼 요청은 각각 1회이며 RECORD_CONFIRMED는 없다. 화면 준비와 Chrome 접근, 두 UI 클릭 요청은 관찰됐지만, 실제 서버 요청 전송·데이터베이스 저장은 수집하지 않으므로 확정할 수 없다. 중간에 웹 문서가 다시 관찰됐다는 근거가 있지만, 이것만으로 모든 확인창이 정상 처리됐다고 단정하지 않는다.

사용자의 마지막 설명은 사진이 ‘자동으로 뜬 창인 것 같다’이다. 이를 수동으로 다시 띄운 창으로 확정하지 않는다. 사진은 확인창의 실제 문구·구성을 보여주지만 앱의 클릭 요청과 사진 촬영의 정확한 선후 관계는 알려주지 않는다. 따라서 확인 클릭이 효과 없이 남았는지, 확인 후 재등장했는지, 후속 사이트 안내가 있었는지는 기존 로그로 구별할 수 없다. 사이트의 자동화 차단 또는 서버 장애로 단정할 근거도 없다.

## 확인한 코드상의 부족과 수정

- 기존 코드는 확인 클릭 반환값을 기록한 뒤 확인창의 사라짐·잔류·재등장을 따로 추적하지 않았다. 확인한 날짜가 가려지는 후속 alert는 DATE_UNREADABLE 대기로 이어졌다. 기존 page_signal이 알려진 Wi-Fi 오류를 포착할 수는 있어도, 사용자에게는 일반적인 시간 초과 안내로 끝났다.
- 현재 화면의 출결 주소와 Chrome의 네이티브 대화상자를 검증한 뒤, 확인창을 최소 600ms 관찰하고 Chrome의 실제 positive button 식별자와 ‘확인/OK’ 레이블을 함께 확인해 한 번 클릭한다. 줄바꿈·공백이 달라도 알려진 퇴실 문구를 인식한다.
- 창 생성 중 메시지가 아직 구성되지 않은 경우를 위해 미분류 안내도 최소 600ms 기다린다.
- 확인 클릭 접수 → 창 사라짐 → 사이트 퇴실 시각 확인을 분리했다. 클릭 후 같은 확인창이 6초 이상 남거나 다시 관찰되면 사유를 남기고 보류한다. 확인 버튼을 임의로 연속 클릭하지 않는다.
- 후속 Wi-Fi/IP 거부, 인증/훈련 대상, 연결/서버 오류, 분류 불가 안내는 날짜 파싱보다 먼저 분류하고 해당 안내로 작업을 종료한다. 추가 안내창을 임의로 승인하지 않는다.
- 진단 버전 4: DIALOG_STATE_CHANGED, dialog_kind, confirm_button_state, confirm_target, confirmation_visible_ms, confirmation_age_ms, confirmation_disappeared 및 Chrome 버전을 추가했다. 대화상자 전이는 최대 12건/시도이며 기존 상세 진단 14건 한도와 별도로 남는다. 본문·계정·쿠키는 업로드하지 않는다.
- 완료 판정은 계속해서 사이트의 오늘 날짜와 실제 퇴실 시각을 읽었을 때만 한다. 접속 횟수·간격 제한과 미확인 클릭 보류는 유지한다.

## 로컬 재현 검증

실제 출결 서버에 요청하지 않았다. 전용 Android 15 / API 35 에뮬레이터와 Chrome 124에서 기존 재현 HTML을 사용했고, DNS 차단과 CDP 로컬 응답을 적용했다. CDP는 앱 대신 확인창을 누르지 않으며, native dialog closed 이벤트와 로컬 제출 횟수를 대조했다.

v0.9.4 기준본은 사이트의 퇴실 응답 0 → Wi-Fi alert를 재현했을 때 확인 요청 1회와 로컬 제출 1회를 거쳐 TIMEOUT_DATE_UNREADABLE로 끝났다. 이때 page_signal은 SITE_NETWORK_RESTRICTION이었다. 수정본은 같은 조건을 SITE_WIFI_REJECTED_DIALOG로 구분한다. 이 재현이 오늘 실제 휴대폰에서 Wi-Fi 거부가 발생했다는 증거는 아니다.

서로 연속해서 뜬 동일 문구의 확인창 사이에 닫힌 화면을 관찰하지 못하면 ‘재등장’이라고 추측하지 않고 ‘계속 보임’으로 기록한다. 에뮬레이터 시험은 실제 갤럭시의 Chrome 버전·확인창 동작이나 학교 서버의 저장 성공을 보증하지 않는다.
